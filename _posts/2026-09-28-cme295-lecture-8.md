# 1\. Introduction to Evaluation

Evaluation is crucial because without measurement, it is impossible to know what to improve in a model. As we transition from traditional discriminative models to generative architectures, we have traded predictable, structured outputs for a "free-form" paradigm. Because a Large Language Model (LLM) can output anything from natural language and Python code to complex mathematical reasoning, universal metrics remain elusive. 

# 2\. Human Evaluation and Its Limitations

Humans rating every response is the "Gold Standard" but is cost-intensive, slow, and subjective. Subjectivity leads to fuzzy ratings. To ensure consistency, researchers use agreement metrics. 

**Agreement Rate** is a metric used to quantify the consistency between different human raters when they are judging model outputs. In other words, the greement rate measures the proportion of time that two or more raters provide the same response for a given pompt. 

For example, in a binary rating task where an output is judged as either "good" or "not good," if two raters agree on the label 80% of the time, the agreement rate is 0.8. 

It is a simple but flawed metric because it does not account for random chance. The lecture provides a methmatical example to illustrate this. We suppose two raters, Alice and Bob, who are both giving random binary responses. If both raters have a 50% probability (P=0.5) of rating an output as "good", the probability that they will agree by pure luck is calcuated as: 

-   P (both say good) + P (both say not good) 
-   ( 0.5 × 0.5 ) + ( 0.5 × 0.5 ) = 0.25 + 0.25 = 0.5

This means raters can achieve a 50% agreement rate without any actual alignment or reasoning because the agreeemnt rate by change is a function of the underlying probabilities of each rater, a raw percentage is difficult to put into context. We cannot easily determine if a specific agreement rate is "good" or "bad" without knowing what the baseline for random chance would have been in that specific scenario. 

To address this limitation, researchers use more sophisticated metrics that make the agreement rate relative to the random chance baseline. 

## Advanced Metrics

**Cohen's Kappa** is used for cases with two raters. If the observed agreemenmt rate is equal to the chance rate, the coefficient is zero. If it is higher, the coefficient is positive. 

**Fleiss' Kappa and Krippendorff's Alpha** are used when there are more than two raters or more complex rating scenarios. 

Coefficient is **positive**

-   The observed agreement rate > random chance baseline.
-   The raters are moving in the right direction.

Coefficient is **0**

-   This means the observed agreement is exactly equal to the agreement rate expected by random chance.
-   The observed agreement rate = random chance baseline.
-   There is no actual consistency in their reasoning

Coefficient is **1**

-   Perfect agreement.
-   The rater's judgements match exactly across every single sample evaluted. 

Coefficient is **negative** 

-   The observed agreement rate < random chance baseline.
-   The raters are disagreeing wit each other.
-   fundamental conflict or confusion in how they are applying the rating criteria.

If these values are near zero or negative, they are served as "health metric", indicating that the evaluation guidelines should be refined, aligning human grades.

# 3\. Rule-Based Metrics

Humans write ideal references for a fixed set of prompts, and the LLM's output is compared to these references, such as **BLEU** (Bilingual Evaluation Understudy), **METEOR**, and **ROUGE**. These metrics calculate n-gram overlap between a model's output and a human-written "reference" text. 

-   **METEOR** is used for translation. It compares unigrams and penalizes incorrect word ordering. 

-   **BLEU** is a percision-focused metric for translation. It includes a brevity penalty to prevent short, gamed translations. 

-   **ROUGE** is primarily used for summarization tasks.

While useful for translation or summarization, they are fundamentally inadequate for generative AI due to two critical factors. These metrics do not account for stylistic variations (different ways to say the same thing) and often correlate poorly with actual human judgement. 

# 4\. LLM as a Judge

The model uses a strong LLM to evaluate the output of another model. The judge receives the prompt, the response, and a specific rubric to return a retionale (explanation) for the assigned score. 

## Set up

**Pointwise**

-   Evaluating a single response (e.g., "is this good or bad?").
-   Evaluate the quality of response → very good 

**Pairwise** 

-   Comparing two responses to determine which is better (useful for perference tuning). 
-   Which one is better:  Response A or Response B?  → Response A

## Steps 

-   **Rationale First** : We instruct the judge to output its reasoning _before_ its numerical score. This allows the model to verbalize its internal critique, which empirically improves grading accuracy.

-   **Structured Output** : Because LLMs are probabilistic, there is no guarantee the judge will return a parsable score. To ensure the output conforms to a schema (like JSON), we use "Structured Output" techniques (constrained decoding) to force the model to sample only from valid tokens defined by the evaluation schema.

-   **Binary Scales** : Binary "pass / fail" scales are often more reliable than granular 1-10 scales.

-   **Calibration** : Periodically compare LLM judge ratings with human ratings to ensure the proxy doesn't diverge from human preference. 

If we want to constrain the decoding process in order to output the response of a given format, There are two attributes, so rationale and score (0 or 1)

## Known Biases 

**Position Bias** : The model may prefer the first response presented. 

-   Solution : Swap the positions of the responses and use majority voting to ensure a stable judgement. 

**Verbosity Bias** : The model prefer longer, more detailed responses regardless of correctness. 

-   Solution : Explicitly instruct the judge to ignore length or apply a length-based penalty in the final score. 

**Self-enhancement Bias** : A model may prefer its own outputs. 

-   Solution : Use a judge with significantly higher capacity than the candidate to ensure the judge can see through stylistic similarities. 

For all evaluation tasks, reproducibility is paramount. We typically set the **Temperature to 0.1 or 0.2** to ensure the evaluation remains stable across multiple runs.

# Best Practices

1\. Crisp guidelines

2\. Binary scale over more granular ones , pass/fail 

3\. White rationale before outputting score 

4\. Mitigate biases

5\. Calibrate with human judgements 

-   Still look at how the model ratings compare with human rating, how the judge is giving with respect to the human ratings. 
    
-   We need the quantity that we want to approximate. 
    
-   Project idea : collect the human ratings, output the LLM-as-a-judge scores, and run some correlation analysis to see if there is something that can be improved in terms of the prompt. 
    

6\. Low temperature for reproducibility 

-   Tweak temperature to make your generation more deterministic as opposed to more creative.
    
-   Researchers use low temperature because they want to make their evaluation experiments reproducible. Common temperature values are 0.1, 0.2.
    

This lecture highlights that evaluation is the engine of LLM improvement. While human evaluation remains the gold standard, its high cost has led to the rise of LLM-as-a-Judge and automated benchmarks. LLM-as-a-Judge is particularly powerful because it provides human-readable rationales and can be constrained to produce structured outputs for easy parsing. However, researchers must remain vigilant against biases like verbosity and position bias.
