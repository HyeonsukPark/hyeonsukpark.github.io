The training of Large Language Models represents a shift from task-specific machine learning to a transfer learning, using massive-scale pre-training followed by targeted alignment. [This lecture](https://www.youtube.com/watch?v=VlA_jt_3Qc4&list=PLoROMvodv4rOCXd21gf0CF4xr35yINeOy&index=5) provides a comprehensive end-to-end process of training Large Language Models (LLM)s. 

# 1\. Pre-Training

In traditional machine learning, models are trained from scratch, independently for specific tasks, such as spam detection. In this case, if we want to work on a different task, such as sentiment extraction, we have to train a completely new model from scratch. There is no shared foundation. Each model starts with zero knowledge and is treated as entirely independent. 

To overcome the limit of traditional machine learning, **Transfer learning** was invented. Instead of training a model from scratch for every task, we start with a model that has already acquired knowledge from prior training (a **pre-trained model**). We then tune the weights of this pre-trained model to adapt it to the specific tasks. Transfor Learning saves time, compute, and data by leveraging previously learned representations rather than starting from zero every time. 

**LLM pre-training** is the highly specialized, computationally massive first stage of the transfer learning pipeline. We train a decoder-only transformer model on raw internet data (Wikipedia, websites, social communities, etc) ranging from hundreds of billions to tens of trillions of tokens. For example, GPT-3 was trained on 300 billions tokens, whereas Llama 3 was trained on 15 trillion tokens. The goal of this stage is simple, predicting the next token. It generates a base model that serves as the rich foundation that will later be tuned for other tasks. 

# Compute Metrics

**flops (Floating Point Operations)** is a unit of compute. It measures the total amount of mathematical operations involved in training a model. Training a LLM requires a massive amount of compute. flops are roughly proportional to the size of the model parameters multiplied by the size of the training dataset (tokens). 

**FLOPS (Floating Point Operations Per Second)** is a measure of compute speed. It tells how fast the hardware (GPU) can execute those operations. GPU technical specifications always highlight the FLOPS capability. 

These metrics are used to quantify how much computational work a model requires and how capable a GPU cluster is of handling it. 

## The Scaling Laws

A research ([Kaplan et al., 2020](https://arxiv.org/abs/2001.08361)) established that model performance improves as compute, data size, and parameter counts increase. In other words, the more compute (flops) we use, the better our model learns to predict the next token. Also, larger models are more sample efficient (Sample Efficiency), meaning they achieve better performance with fewer tokens compared to smaller models. 

## Chinchilla Laws

Since compute is limited, we cannot just scale parameters indefinitely without enough data to match. According to "Training Compute-Optimal Large Language Moels" paper ([Hoffmann et al., 2022](https://arxiv.org/abs/2203.15556)), it revised scaling expectations, suggesting that for every doubling of compute, the model size and training data should scale equally. The optimal ratio is roughly 20 tokens per parameter. 

# 2\. Training Optimizations

## Training process

The process of training a Large Language Model consists of three steps: forward pass, backward pass, and weight update. 

### 1\. Forward Pass

The Forward Pass is the stage where raw data is fed into the model to see what it predicts, through the layers of the model. At the end of the network, the model outputs its prediction which is compared against the actual target text (ground truth or label) using a loss function. The resulting loss is a single number that quantifies exactly how incorrect the model's prediction was. As data passes through each layer, the intermediate calculation values, **Activations**, are temporarily saved and will be used later to compute the gradidnets during the backward pass. The memory required during the forward pass depends on model size, batch size, and context length. 

### 2\. Backward Pass

Once the loss has been calculated, the model figures out how to correct its mistake. Starting from the final loss calculation, the model works backward through its layers. It calculates "**Gradient**", understanding how changing each individual weight would affect the final loss. The gradient is a mathematical vector that points in the direction where the loss is minimized.  

### 3\. Weight Update

Once the model has calculated the gradients and knows which direction will reduce the loss, it adjusts its parameters. The model applies the calculated gradients to its original weights, tweaking them slightly so that the next time it sees similar data, its prediction will be more accurate. In this step, Adam optimizer tracks the current gradients and running historical statistics to make training more stable. 

While directly substracting the gradient from the weights is the standard baseline for adjusting parameters to minimize loss during the backward pass, LLM training pipelines typically use more sophisticated optimizers like Adam. However, storing these optimizer states requires a massive amount of memory, representing a significant portion of the totla GPU memory. 

## Parallelism

During training, memory must hold model weights, activations (saved during the forward pass to compute the loss), gradients (direction of loss minimization), and optimizer states. However, GPU memory is highly restricted. To overcome these problems, several distribution methods are used. 

**Data Parallelism (DP)** 

It distributes data across GPUs, so that this forward pass and backward pass can be implemented independently. The training batch is split across multiple GPUs, each running a full copy of the model. Gradients are averaged and communicated between GPUs. 

**ZeRO (Zero Redundancy Optimizer)** 

Rather than duplicating the model on every GPU, ZeRO shards the optimizer states (ZeRO-1), gradients (ZeRO-2), and model parameters (ZeRO-3) across the GPU cluster. This cuts memory usage at the cost of increased communication. 


It splits the model itself within a single training batch. 

-   Tensor Parallelism shards large individual matrix multiplications across GPUs. 
-   Pipeline Parallelism distributes sequential layers across different GPUs (GPU 1 handles layers 1-3, GPU 2 handles 4-6). 
-   Expert Parallelism : In Mixture of Experts (MoE) architectures, different experts are distributed across different GPUs. 

# Optimization via Flash Attention

**Flash Attention** is an algorithm that makes the self-attention calculation faster and more memory-efficient without making any mathematical approximations. 

GPUs have **HBM** (High Bandwidth Memory, large but slow) and **SRAM** (on-chip memory, extremely fast but tiny). The core difference between standard self-attention and Flash Attention is how they utilize GPU memory to calculate attention.

## Standard Self-Attention

During calculation, the GPU reads and writes intermediate matrices back and forth to its HBM. Because HBM is large but slow, this data transfer becomes a massive bottleneck. 

## Flash Attention

It avoids this bottleneck using a method called tiling. It splits the matrices into small blocks, loads them into the GPU's SRAM, and computes the attention step-by-step. By reducing reads and writes to the slow HBM, training runtimes are significantly shortened. Computing attention is SRAM is so fast, the model no longer needs to save memory-heavy activations during the forward pass. Instead, it simply recomputes them during the backward pass, saving GPU memory.

## Mixed Precision Training

The goal is to save massive amounts of GPU memory and accelerate training times without degrading the final performance of the model. 

Hardware runs faster when processing lower-precision numbers. For example, on GPUs, running computations in a highly precise format like FP64 is much slower, whereas dropping to lower-precision formats can increase the speed. Mixed precision training takes advantage of this speedup. 

-   FP32 (32-bit single precision) : It uses 32 bits to store a single number, providing high mathematical precision and granularity. 

-   FP16 (16-bit half precision) : It uses only 16 bits to store a number. Because it uses half the bits, it requires half the memory footprint of FP32, though it is less precise. 

1\. **The Setup** : Initially, the model's weights are stored and maintained in high-precision FP32.

2\. **The Forward Pass** : The FP32 weights are temporarily cast down to FP16. Calculating activations is executed in this lower FP16 precision. This reduces memory consumption and speeds up the forward pass. 

3\. **The Backward Pass** : The gradients (the directions needed to minimize the model's loss) are also calculated and stored in lower-precision FP16. 

4\. **The Weight Update** : Once the gradients are computed, they are used to update the weights back in high-precision FP32. 

# 3\. Supervised Fine Tuning

Once a base model is pre-trained, it undergoes **Supervised Fine-Tuning (SFT)** and Instruction Tuning. SFT uses high-quality, labeled pairs of input and output. Unlike pre-training, which uses the whole sequence for the loss function, SFT only calculates loss on the output tokens (the response), not the user's prompt. 

**Instruction Tuning** is a subcategory of SFT that teaches the model to behave as an interactive assistant. It rains on diverse data mixtures like story writing, list generation, code explanations, and safety alignment.  

Safety behavior, such as refusing to answer harmful prompts or using nuanced hedging language, is trained directly into the model's weights during SFT. In this stage, specialized data mixtures are used. The data mixtures can be both human-written and synthetic data.   

# 4\. Parameter-Efficient Fine-Tuning with LoRA

As SFT is computationally expensive with big GPUs, we need to apply parameter-efficient methods like **LoRA (Low-Rank Adaptations)** to solve the problem. Tranditionally, if we wanted to adapt a pre-trained LLM to a specific tasks, we had to update every single one of its billions of parameters. This approach is computationally expensive, with storage inefficiency. For example, if we have ten different tasks (Task1, Task2, Task3, ....), we have to save ten separate, full-sized copies of the billion parameter model. 

**1\. One Frozen Base Model** 

First, let's say that we have ten different tasks. We just keep one copy of the massive, pre-trained base model. These weights are completely frozen and never change during training 10 tasks. 

**2\. Ten Task-Specific B and A matrices** 

For each of the 10 different tasks (such as spam detection, sentiment extraction,etc), we train a separate, low-rank matrices, B and A. 

**3\. Adding outputs** 

When an input comes in for Task 1, we route it through the frozen base model and the Task 1 A / B matrices, adding their output (W0 +  B x A) together. If we want to switch to Task 2, we simply unload the Task 1 A / B matrices and load the Task 2 A / B matrices.

The A and B matrices are extremely small (due to their low rank R), they are cheap to store and fast to swap out. Instead of storing 10 independent, multi-billion parameter models, we store just 1 giant base model and 10 tiny, lightweight matrices. 

While the original LoRa paper applied updates only to attention weights, recent findings show that applying LoRA to feed-foward network (FFN) blocks actually yields the most performance benefits. 

## QLoRA (Quantized LoRA) 

In LoRA, even though the base model weights are frozen, they still take up a lot of memory. QLoRA solves this by compressing the frozen base model down to a highly efficient 4-bit format. To do this without losing the model's performance, it uses a specialized format called **NormalFloat4 (NF4)**.

In standard quantization, numbers (weights) are evenly distributed, in fixed sizes. However, weights for LLM follow a normal distribution. NF4 assums the model's weights are normally distributed and splits the space into quantiles rather than fixed-size buckets. The buckets near the center of the bell curve (with most weights) are made very narrow and precise. The buckets near the outer tails (with rare weights) are made much wider. With this approach, it optimizes the bits used for encoding, since every single bucket is used to its maximum capacity.

However, this compression still degrades its performance. QLoRA avoids this by splitting the precision of the system. 

-   Frozen base model is stored in 4-bit NF4 to save momery
-   Tiny, active LoRA matrices (A and B) are calculated and updated in full precision BF16.

This allows the model to keep its performance completely intact.
